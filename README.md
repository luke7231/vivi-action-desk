# VIVI Action Desk

OrbitCRM의 AI 검색 관측을 **주제 판단 → 질문 근거 → 액션 → 상태 관리**로 연결하는 로컬 MVP입니다. 버블쉐어 Product Engineer 채용 과제의 합성 데이터셋 v2를 사용합니다. 실제 AI 검색·고객 행동 측정값이 아닙니다. [문제 정의·성공 기준·개선 내역](PRODUCT.md)을 먼저 보면 설계 의도를 빠르게 이해할 수 있습니다.

[3분 데모](DEMO.md)와 [추천 분기 점검](EVALUATION.md)을 함께 제공합니다. 제공된 채용 평가용 합성 JSON 데이터는 로컬 재현을 위해 포함했습니다. 원본 과제 안내 PDF와 개인 면접 메모는 공개 저장소에 포함하지 않습니다.

## 3분 실행

필요: Node.js 20.9 이상, npm, Python 3.9 이상. 유료 API 키나 외부 DB는 필요하지 않습니다. 두 서버는 `127.0.0.1`에만 바인딩되고 프론트엔드는 Vite의 같은 출처 `/api` 프록시를 사용합니다. CORS·인증·고객별 접근 제어는 없는 **로컬 데모**이며 외부 네트워크에 공개하는 설정이 아닙니다.

```bash
npm ci
python3 server.py          # 터미널 A: http://127.0.0.1:8000
npm run dev                # 터미널 B: http://127.0.0.1:5173
```

브라우저에서 `http://127.0.0.1:5173`에 접속합니다. 첫 실행 시 `vivi.sqlite3`가 생깁니다. 재시작해도 액션은 남습니다. 깨끗한 재실행이 필요하면 서버를 끄고 해당 DB 파일을 다른 이름으로 옮긴 뒤 시작하세요.

```bash
npm run build              # TypeScript 검사 + 프로덕션 프론트엔드 빌드
npm test                   # 데이터 품질·캐시·DB 재열기 테스트
npm run cost               # 제공 단가로 원가/마진 재계산
python3 scripts/evaluate_recommendations.py  # 합성 사례 추천 분기 점검
```

기본 포트가 사용 중이면 터미널 A에서 `PORT=8001 VIVI_DB=/tmp/vivi-demo.sqlite3 python3 server.py`, 터미널 B에서 `VIVI_API_PORT=8001 npm run dev -- --port 5174`로 실행하고 `http://127.0.0.1:5174`에 접속합니다. 두 서버를 모두 실행한 뒤 브라우저를 엽니다.

## 해결하려는 문제와 가치

언급률만 보면 마케팅 담당자는 어떤 주제에 집중할지, 왜 그 주제를 골랐는지 설명하기 어렵습니다. 수집 실패를 미노출로 오인하거나 부정적 제품 언급을 콘텐츠 부족으로 잘못 처방할 수도 있습니다. 주제별 큐에서 정상 관측 분모와 경쟁사·인용·부정 언급을 확인한 뒤 질문 원본 증거로 내려가 행동을 선택합니다.

**가설:** 출처가 보이는 우선순위와 즉시 저장 가능한 액션이 있으면 분석에서 실행 계획까지 걸리는 시간이 줄어든다. **검증 계획:** 담당자 5명에게 상위 질문 5개를 보여 주고, 근거를 이해해 액션을 만들기까지의 시간과 근거 설명 성공률을 기존 표 형태 분석과 비교한다. **성공 기준(사전 제안):** 중앙값 시간 30% 감소, 근거 설명 성공률 80% 이상, 잘못된 단정 0건. 사용자 실험은 하지 않았으므로 달성 주장도 하지 않는다.

## 구현과 설계 판단

- React + TypeScript + Vite UI, Python 표준 라이브러리 HTTP API, SQLite 영속 저장. Python은 과제에서 허용한 Node.js 동등 서버 환경으로 사용했습니다. 별도 DB 서비스 없이 재현 가능합니다.
- `GET /api/topics`, `GET /api/topics/:id`: 주제별 판단·coverage·점수 구성. `GET /api/questions?q=&topic=`, `GET /api/questions/Q008`: 질문 목록과 채널별 원본 근거. `GET /api/actions`, `POST /api/actions`, `PATCH /api/actions/:id`: 액션 생성·조회·상태 변경.
- 액션 제목 3~160자, 메모 1000자, 담당자 80자, 실행 완료·후속 관측 기준 각각 3~300자, 유효한 질문/근거 버전/요청 번호와 허용 상태만 받습니다. 잘못된 값은 400, 없는 항목은 404, 변경된 근거나 중복 액션은 409를 반환합니다. API 중단 중 입력을 유지하고 한국어 오류와 재시도를 표시합니다.
- 주제 우선순위 = `평균 importance_score × 정상 관측 중 미언급 비율 × (1 + min(평균 estimated_monthly_interest, 3000)/6000) × coverage` 반올림. 질문별 점수는 같은 식에서 coverage 항을 빼고 계산합니다. 질문의 월 관심도를 서로 독립 수요로 합산하지 않습니다. 중요도와 관심도는 데이터셋의 **가상 값**입니다. coverage가 80% 미만인 주제와 정상 관측 2건 미만인 질문은 수집 점검으로 분기합니다. 부정 언급은 제품 점검, 전부 언급되면 유지입니다. 규칙은 원인 진단이 아닌 설명 가능한 **검토 가설**입니다.
- 비슷한 의미의 Q001/Q002, Q056/Q057, Q066/Q067에는 중복 콘텐츠 작업 경고를 표시합니다. 액션은 자동 생성하지 않으며 사용자가 선택합니다. 실행 완료 기준과 후속 관측 기준은 별도 필드로 남겨 페이지 수정 완료를 검색 성과 달성으로 오인하지 않습니다.
- API의 규칙 계산 결과를 SQLite에 캐시합니다. 키에는 질문 ID, 선택된 최신 관측 ID, 룰 버전, 모델·프롬프트 버전 자리값이 포함됩니다. 새 수집으로 관측 ID가 바뀌거나 룰 버전을 올리면 새 키를 사용합니다. 액션은 이 키와 스냅샷 ID를 함께 저장합니다. 동일 요청 번호의 동시 재시도는 한 레코드로 처리합니다. 현재는 원본 데이터가 정적이므로 자동 수집 파이프라인은 없습니다.

### 업무용 대시보드 화면

최초 화면의 큰 히어로 문구, 영문 장식 레이블, 반복되는 연녹색 카드와 긴 세로 흐름을 제거했습니다. 현재 화면은 **좌측의 실제 동작하는 분석·액션 내비게이션 → 짧은 상단 컨텍스트 → 구분선으로 묶은 핵심 수치 → 검색 가능한 주제·질문 목록 → 선택 근거와 액션 작성 탭** 순서입니다. 액션 저장 후에는 상태를 바로 바꿀 수 있는 목록으로 이동합니다. 데스크톱에서는 목록과 상세를 각각 스크롤하고, 좁은 화면에서는 한 열로 배치합니다.

시각 기준은 [토스페이먼츠 상점관리자 공개 안내와 가이드](https://docs.tosspayments.com/resources/glossary/dashboard), [토스쇼핑 성과 대시보드 공개 예시](https://shopping-docs.toss.im/ads/performance/intro/overall), [TDS의 색상](https://tossmini-docs.toss.im/tds-mobile/foundation/colors/)·[타이포그래피](https://tossmini-docs.toss.im/tds-mobile/foundation/typography/)를 직접 확인했습니다. 공개 예시에서 관찰한 업무별 내비게이션, 분리된 숫자 요약, 검색·목록·선택 상세, 절제된 파란 주요 행동을 VIVI의 데이터 흐름에 맞게 해석했습니다. 공개 가이드의 화면은 발행 시점의 예시이며 현재 토스 PC 제품의 정확한 치수나 전체 토큰이라고 주장하지 않습니다. 로고와 서비스 정체성도 사용하지 않았습니다.

### 데이터 품질 판단

456개 관측에서 `(question_id, channel, source_snapshot_id)`별 최신 타임스탬프·ID를 남기면 450개입니다. 그중 partial 12, failed 5, 응답 언어 불일치 3을 제외한 430개만 신뢰 가능한 관측입니다. 최신 스냅샷은 225개 중 212개가 정상, 13개는 미확인입니다. 수집 실패를 **미언급으로 계산하지 않습니다**. `target_mentioned`, `mention_count`, `citation_count` 요약값은 원본 `mentions`·`citations`와 다를 수 있어 판정에 사용하지 않습니다. 출처 소유 `brand_id`가 비어 있으면 도메인만 보고 자사 소유라고 확정하지 않습니다. 인용 제목이 비어 있으면 도메인을 보여 줍니다.

최신 정상 관측 전체의 자사 언급은 **63/212**입니다. 업무 자동화 주제는 15/15에서 자사가 언급되어 유지 판단입니다. 보안·권한은 자사 언급 0/12이지만 확인된 자사 소유 인용이 6건이라 공식 콘텐츠가 없다고 단정하지 않습니다. `SRC024`는 도메인이 자사처럼 보여도 `brand_id`가 비어 있어 소유 미상으로 둡니다. 모바일은 8/15 언급 중 부정 언급 5건이라 제품 불만 점검이 먼저입니다. 확장성은 정상 9/15, 미확인 6/15라 일부 질문에서 재수집 판단이 필요합니다. 이는 합성 데이터 관측 사실이며 원인 진단이나 효과 예측은 아닙니다.

## 비용과 품질

고정 단가는 `source/VIVI_MVP_Sample_Dataset/pricing_assumptions.json`에서 읽습니다. 구독 $100, 고객당 월 분석 요청 1,000회, 초기 100개사, 목표 원가 $20 이하/마진 80% 이상입니다. 주 1회 수집 968건의 표 기준 원가 $3.87과 인프라·DB $6을 유지합니다.

| 구조 | AI-M | 외부 분석 API | 수집 | 인프라 | 고객당 월 원가 | 마진 |
|---|---:|---:|---:|---:|---:|---:|
| 기준: 요청마다 두 호출 | $18 | $12 | $3.87 | $6 | **$39.87** | **60.13%** |
| 구현: 원본 데이터 규칙 계산 + 캐시 | $0 | $0 | $3.87 | $6 | **$9.87** | **90.13%** |

구현에서는 모델·외부 분석 API를 **호출하지 않습니다**. Mock 호출의 비용을 0으로 처리한 게 아니라, 해당 유료 작업을 원본 JSON 조인과 명시적인 규칙으로 대체했습니다. 과제는 규칙 기반 대체를 허용하며 특정 모델 호출을 필수로 요구하지 않습니다. UI 조회·상태 변경은 과제 정의상 분석 요청에 포함되지 않습니다. 캐시는 반복 계산 비용과 응답 시간을 줄이지만 기준 단가표에는 CPU 단가가 없어 표의 직접 원가 절감액은 호출 생략에서 나옵니다. 주간 수집 비용은 로컬에서 실제 결제하지 않아도 고정 단가로 계상했습니다. 100개사면 월 직접 원가 $987, 매출 $10,000, 매출총이익 $9,013입니다. 같은 조건의 1,000개사라면 표상 원가 $9,870입니다. 고객당 분석 요청이 2,000회가 되어도 규칙 경로에는 추가 모델/API 요금이 없지만, 실제 CPU·DB 용량과 $6 인프라 배분이 유지되는지는 운영 측정이 필요합니다.

**품질 영향:** 원본 mentions·citations에서 언급/출처를 결정하므로 제공 데이터의 요약 필드 불일치에 영향을 받지 않습니다. 다만 규칙 추천은 AI-M의 원인 진단 정확도 81%, 액션 초안 채택률 68%와 동등하다고 주장할 근거가 없습니다. 현재 규칙은 관측된 언급·인용·부정 감성에 대한 설명만 하며 인과적 원인 진단은 하지 않습니다. 75개 질문의 최신 관측에서 규칙은 개선 62, 유지 9, 부정 언급 점검 3, 재수집 1로 나뉩니다. 이는 **분기 커버리지 확인**이지 추천의 채택률이나 정확도 실험 결과가 아닙니다. 자유로운 원인 진단이 필요한 질문에서 규칙의 근거 설명이 부족하거나 담당자의 채택률이 낮다는 사용자 검증이 나오면 유료 모델을 제한된 경로로 실험하겠습니다. AI-M+API 쌍의 유료 miss는 월 최대 337회까지 허용되며, 재사용률 66.3% 이상을 실제 트래픽에서 확인해야 목표 원가를 지킬 수 있습니다. 캐시 적중률은 측정하지 않았고 가정하지 않습니다.

표의 $9.87은 제공된 **구조화된 라벨 데이터**와 고정 단가·주간 수집 빈도를 전제로 한 설계 추정치이며 운영 청구액이 아닙니다. 향후 원문 답변에서 언급·감성·인용을 추출하는 작업, CPU·DB 부하 증가, 고객별 인프라 배분 변경은 이 단가표에 계상되지 않았습니다. 규칙 판단의 예시·반례·제외 사례와 단순 미언급 기준선 비교는 [추천 분기 점검](EVALUATION.md)에 기록했습니다. 이 결과는 추천 정확도나 실제 사용자 성과가 아닙니다.

## 검증 기록

`npm run build`, `npm test`(7개 통과), `npm run cost`를 실행했습니다. 테스트는 중복·미확인 분모, 주제별 다른 판단, 유사 질문 표시, 요약값 불일치, 근거 수정과 룰 버전에 따른 캐시 무효화, SQLite 재열기·이전 스키마 마이그레이션, 액션 입력 제한·404·409, 동일 요청의 동시 재시도를 확인합니다. 리디자인 후 Chrome에서 [1366px 실제 대시보드](evidence/05-dashboard-redesign.png)와 [390px 상세 화면](evidence/06-mobile-dashboard.png)을 캡처했습니다. 조회→주제 선택→검색→질문 근거→액션 작성→저장→상태 변경→새로고침 후 유지가 동작했습니다. API를 중단한 상태에서 액션 생성 실패 시 담당자 입력이 남았고, 서버 복구 후 재시도하여 한 건만 저장됐습니다. 좁은 화면의 가로 잘림과 키보드 포커스 표시를 점검했습니다. 검증은 로컬 브라우저와 합성 데이터에 한정됩니다.

추가 QA는 같은 Mac의 새 압축 해제 폴더와 빈 npm 캐시에서 `npm ci`(온라인), 빌드·7개 테스트·원가 계산을 재실행했습니다. 임시 SQLite와 별도 포트에서 API 400/404/409, 동일 키 동시 요청의 단일 저장(201·200), 브라우저의 서버 중단 오류·입력 보존·복구 후 재시도·서버 재시작 후 상태 유지도 확인했습니다. 추천 평가 14건 중 기대 분기 14건 충족, 단순 기준선 9건 충족이며 판단 불가 2건은 제외했습니다. 이는 같은 기기에서의 재현 검사이고 다른 운영 체제나 실제 고객 부하 검사는 아닙니다.

## 범위와 한계

현재 앱은 OrbitCRM 한 고객, 제공된 두 스냅샷, 최신 스냅샷의 주제·질문 분석에 집중합니다. 실제 AI 수집, 유료 분석 API, 로그인/다중 고객, 배포, 사용성 실험, 자동 효과 측정은 없습니다. 데이터의 모든 `.example` 주소는 합성 주소라 외부 링크 대신 `OBS`/`SRC` 식별자를 표시합니다. LLM 실행이나 실제 고객 성과를 주장하지 않습니다. 우선순위와 문구는 정적 가설이므로 담당자 검토 후 실행해야 합니다.
